## 5.1 对比表

| 后端 | 隔离强度 | 冷启动 | 适合场景 |
|---|---|---|---|
| Docker 容器 | 弱（共享内核） | 快 | 单租户、可信代码、开发起步 |
| Linux namespaces / bwrap | 弱～中（共享内核） | 极快 | 本地、单机、教学 |
| gVisor | 中 | 中 | 多租户但不想上 VM |
| Firecracker microVM | 强 | 快（~百 ms） | 生产多租户首选 |
| 完整 VM | 强 | 慢 | computer-use / 需要完整 OS |
| WASM | 中（语言级） | 极快 | 轻量函数、Edge 执行 |

## 5.2 选择口诀

> **可信代码 → Docker；不可信 / 多租户 → microVM 或 gVisor；只要轻量函数 → WASM；要完整电脑 → 完整 VM。**

## 5.3 为什么「容器不够」

容器共享宿主机内核。一旦内核有漏洞，或配置不当（`--privileged`、挂载了 `docker.sock`），就可能**逃逸到宿主**。

多租户场景下，A 客户的代码不该有机会碰 B 客户，容器给不了这个保证，microVM 可以。

## 5.4 一条实用的升级路径

```
本地开发      Docker / bwrap        ← 快、够用、单机
   │
小规模上线    gVisor / Kata
   │
生产多租户    Firecracker microVM   ← 强隔离 + 快启动
   │
需要完整 OS   QEMU/KVM 完整 VM      ← computer-use
```

## 5.5 除了隔离强度，还要看什么

| 维度 | 影响 |
|---|---|
| 冷启动 | 决定用户体验与能否用「预热池」 |
| 兼容性 | 系统调用被拦截越多，程序越容易跑不起来 |
| 资源开销 | 每环境的内存 / CPU 占用，决定单机密度 |
| 运维复杂度 | microVM 编排比容器复杂 |
| GPU 支持 | 大模型 Agent 场景的关键 |
