> 这是全教程最「能直接用于决策」的一章。隔离后端决定了**安全上限、启动速度、兼容性和成本**。
> 读完你应该能回答：我的场景到底该用容器、gVisor、microVM，还是完整 VM？

## 5.1 对比表

| 后端 | 隔离强度 | 冷启动 | 单机密度 | 兼容性 | 适合场景 |
|---|---|---|---|---|---|
| Docker 容器 | 弱（共享内核） | 快（~百 ms） | 高 | 最好 | 单租户、可信代码、开发起步 |
| Linux namespaces / bwrap | 弱～中（共享内核） | 极快 | 高 | 好 | 本地、单机、教学 |
| gVisor | 中 | 中（数百 ms～秒） | 中 | 中（系统调用被拦截） | 多租户但不想上 VM |
| Kata Containers | 强 | 中 | 中 | 好 | 想用容器接口 + VM 隔离 |
| Firecracker microVM | 强 | 快（~百 ms） | 高 | 好 | 生产多租户首选 |
| 完整 VM (QEMU/KVM) | 强 | 慢（秒级） | 低 | 最好（完整 OS） | computer-use / 需要 GUI |
| WASM | 中（语言级） | 极快 | 极高 | 差（仅支持编译到 WASM 的语言） | 轻量函数、Edge 执行 |

> 注意「隔离强度」和「兼容性」通常**反向相关**：隔离越强，能拦截的系统调用越多，程序越容易跑不起来。

## 5.2 选择口诀

> **可信代码 → Docker；不可信 / 多租户 → microVM 或 gVisor；只要轻量函数 → WASM；要完整电脑 → 完整 VM。**

更细一点的判断顺序：

```
要跑任意代码吗？
├─ 否 → 不需要沙箱（见第 8 章）
└─ 是
   ├─ 需要完整 OS / GUI / 桌面应用吗？
   │  ├─ 是 → 完整 VM（computer-use）
   │  └─ 否
   │     ├─ 只是短小、确定性的函数吗？
   │     │  ├─ 是 → WASM
   │     │  └─ 否
   │     │     ├─ 用户之间互不信任 / 面向公众吗？
   │     │     │  ├─ 是 → microVM（Firecracker）或 gVisor
   │     │     │  └─ 否 → Docker / bwrap 够用
```

## 5.3 为什么「容器不够」

容器共享宿主机内核。所有容器都通过**同一个内核**发起系统调用，一旦内核有漏洞，或配置不当，就可能**逃逸到宿主**：

- `--privileged`：等于把宿主权限交给容器；
- 挂载 `docker.sock`：容器能创建新容器，等于拿到宿主的控制权；
- 内核 0-day：容器之间没有内核级边界，一个租户能攻击另一个。

多租户场景下，A 客户的代码**不该有机会碰到** B 客户。容器给不了这个保证；**microVM 可以**——每个环境有独立内核，逃逸要同时攻破内核和 hypervisor。

## 5.4 gVisor 与 microVM 的区别

两者都加强隔离，但走的是**不同路线**：

| | gVisor | microVM（Firecracker） |
|---|---|---|
| 思路 | **用户态内核**：拦截并重新实现系统调用 | **独立内核**：每个环境一个精简内核 |
| 隔离边界 | 应用 ↔ 用户态内核 | 环境 ↔ hypervisor |
| 攻击面 | gVisor 自身的实现（较大） | hypervisor（较小） |
| 兼容性 | 部分系统调用未实现 → 可能跑不起来 | 接近原生 Linux |
| 资源开销 | 较低 | 每个 VM 有内核开销 |
| 启动 | 中 | 快（优化后 ~百 ms） |

**怎么选**：兼容性要求高、要求「像真机」→ microVM；想省内存、能接受偶发的 syscall 不兼容 → gVisor。Kata Containers 则是「用 VM 承载容器」，让你保留容器工具链的同时拿到 VM 隔离。

## 5.5 一条实用的升级路径

```
本地开发      Docker / bwrap        ← 快、够用、单机
   │
小规模上线    gVisor / Kata
   │
生产多租户    Firecracker microVM   ← 强隔离 + 快启动（推荐终态）
   │
需要完整 OS   QEMU/KVM 完整 VM      ← computer-use / GUI
```

**要点**：不要一步到位。先用容器把产品跑通，等出现**多租户 / 不可信**需求时再升级后端。升级时控制面接口不变，只换数据面实现——这正是第 4 章「控制面与数据面分离」的价值。

## 5.6 除了隔离强度，还要看什么

| 维度 | 影响 | 决策提示 |
|---|---|---|
| **冷启动** | 决定体验与能否用「预热池」 | 要求 <1s 响应就别用完整 VM |
| **兼容性** | 隔离越强越可能牺牲兼容性，gVisor 风险最高 | 在目标镜像上先做一次兼容性验证 |
| **资源开销** | 每环境内存 / CPU，决定单机密度与成本 | 高密度场景 gVisor / 容器更省 |
| **运维复杂度** | microVM 编排比容器复杂 | 小团队优先托管方案 |
| **GPU 支持** | 大模型 Agent 的关键 | Firecracker 等极简 microVM 通常**不支持 GPU 直通** → 用完整 VM / Kata / 托管 GPU 沙箱 |
| **生态与文档** | 排查问题的时间成本 | 选活跃项目，别选孤品 |

## 5.7 场景速查

| 场景 | 推荐后端 | 理由 |
|---|---|---|
| 内部团队的数据分析 Agent | Docker（+ 断网） | 可信用户、代码大体可控，够用且便宜 |
| 面向公众的在线代码执行平台 | Firecracker microVM | 不完全信任用户，安全 = 产品生命线 |
| 浏览器自动化 / computer-use | 完整 VM（或容器 + Playwright） | 需要完整 OS 与 GUI |
| 边缘轻量函数 | WASM | 启动极快、资源极小 |
| 本地教学 / 原型 | bwrap / namespaces | 零依赖、无需 root |
